# Emergent feasibility review — 2026-11-07

**Status:** Conditional technical GO for controlled validation; NO authorization for backend build or production launch. **Decision #35 remains unchanged pending explicit builder selection.**

## Evidence
User shared a 162-line read-only report generated by Emergent for its existing ForFathers frontend. Emergent reported no code, configuration, service, or deployment changes. Current project remains frontend-only with mock data; none of eight backend workflows has been built or tested.

## Report's proposed architecture
Emergent app/backend with MongoDB, Stripe, email service, and private Cloudflare R2 or S3 for paid downloads. Alternative: Emergent frontend with Supabase Auth/Postgres/private storage and Stripe. Emergent preferred native stack because the present app uses it.

## Feasibility (all untested)
- $5 monthly subscriptions: custom Stripe subscription API, webhook verification, paid-through access and cancellation.
- $3/$5 guest digital sales: verified Stripe payment, protected fulfillment, emailed recovery.
- Five-download limit: atomic per-purchase increment and expiring download authorization.
- Member library/community: per-route authorization, moderation, account deletion.
- $1 giving reserve: idempotent ledger, refund/dispute reversals, quarterly reconciliation, legal review mandatory.
- Hosting/export: GitHub export reportedly requires a paid tier; backup/export and external deployment not demonstrated.

## Red-team findings
1. **Authentication:** Report suggests custom password hashing/JWT login. Evaluate proven managed authentication first; do not treat writing authentication as default low-risk.
2. **Download semantics:** A presigned URL may be reused until expiry. Define a 'download' and enforce count at secure authorization; clarify retries, concurrent access, failed transfer, token reuse and recovery. Test 20 concurrent attempts; exactly five authorizations permitted. Do not promise single-use S3/R2 links without server-side enforcement.
3. **Storage:** Emergent object storage reportedly has no delete and does not travel with exported code. Verify private R2/S3 lifecycle/deletion and serving design before coding.
4. **Production operations/pricing:** Support-assistant plan claims explicitly marked unverified. Independently confirm domain, deploy, credit consumption, scheduler, DB backups/restore, data export, email verification and payment fees via primary account/provider documentation.
5. **Architecture lock:** D035 builder and existing Supabase-oriented implementation spec cannot silently change to MongoDB or custom auth. Requires explicit ADR with rationale/security/portability/cost risks.
6. **Legal launch blockers:** Giving Fund legal structure, terms/privacy/refunds, community governance, verified payment and email domains.

## Recommended next gate
One narrow no-code verification of actual Emergent project configuration and managed-auth options, production/deployment terms, GitHub export, private storage and Stripe subscription support. Then select backend architecture with an explicit decision. Only after that authorize a **Stripe test-mode vertical slice**: sign up/login, purchase/subscribe, server-verified webhook, gated access; digital delivery as next controlled slice.

## Verification requirements
Stripe test-clock renewal/failure/cancel; duplicate/out-of-order webhooks; guest purchase and recovery; private/expired links; 20 simultaneous download authorizations; member-route access tests; backup restore; portability outside Emergent; cost confirmation and full launch checklist.

**Source:** Emergent read-only report pasted by user, 2026-11-07; report self-reports that platform-support pricing details were unverified.

## Follow-up: independent official documentation verification (2026-11-07)

- **Critical correction:** Emergent has built-in **Emergent Auth**, including email/password, Google and managed sessions. The report's assumption that custom password/JWT auth is necessary is **incorrect as a platform-wide assertion**. Still validate suitability in this *particular* project, authorization isolation, account deletion and migration/export. Source: https://emergent.sh/docs/add-login-user-accounts and https://help.emergent.sh/add-login-user-accounts
- **Stripe:** official integration catalogue explicitly says accepting payments and managing subscriptions are supported; the report's statement that a specific `emergentintegrations` helper lacks subscription handling may still be accurate. Subscription code should use documented Stripe SDK and signed webhooks rather than assume the helper provides lifecycle management. Source: https://help.emergent.sh/key-integrations-catalogue
- **Pricing:** official https://emergent.sh/pricing lists Free 10 monthly credits, Standard **$20/mo billed annually** and 100 monthly credits, Pro **$200/mo billed annually** and 750 credits; billing cadence and account-specific prices still require confirmation. https://help.emergent.sh/deploying-web states Starter published app uses **50 credits/month** (publishing tiers vary). A 50-credit deployment would consume 50% of Standard's monthly allowance. Not equivalent to $50 cash; do not promise a specific monthly price for a billing cadence other than annual.
- **Credit spend:** https://help.emergent.sh/managing-credit-usage confirms code generation, tests, integrations and publishes consume credits; set per-prompt credit limits before implementation and review actual usage.
- **Portability:** https://help.emergent.sh/your-data-ownership and https://help.emergent.sh/faqs confirm GitHub push on Standard+, but code export does **not** include environment variables, secrets or production database records. FAQ says production DB export is not currently self-service; independently verify usable mongodump access and restore before architecture lock. Hosting portability of **managed Emergent Auth** has not been established; treat as a lock-in risk.
- **Custom domain:** official https://help.emergent.sh/custom-domain describes DNS and SSL path for published apps.
- **Production caveat:** preview and production instances/data can be distinct; document configuration before first publish (https://help.emergent.sh/the-chat-to-deployment-flow).

### Updated recommendation
**Do not approve custom authentication.** Candidate low-complexity architecture: Emergent Auth + native application backend/MongoDB + Stripe SDK + independently controlled private digital-product storage (R2/S3) + transactional email, *conditional* on testing authorizations, account/data portability and operating costs. The architectural switch from Supabase still requires an explicit decision; no code or publication authorized.
